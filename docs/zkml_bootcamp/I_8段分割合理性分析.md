# I · Prove 8 段分割（①~⑧）合理性分析 —— 从日志实测 + 数据传输逻辑判定

> **定位**：回答"文档 D 的 ①~⑧ 分段，作为『把证明放到多块 FPGA 硬件』的分割边界是否合理"。判定依据两条独立证据链：
> 1. **日志实测时序**（`zkml/gpt2_512.log`、`zkml/gpt2_1024.log`，脚本 `zkml/tools/extract_prove_timing.py` 还原）；
> 2. **数据传输逻辑**（文档 D §0.3 三根贯穿线 + 附录 B 算子数据流）。

## 1. 先从"日志里到底能测出什么"建立判据

prove 的 ①~⑧ **不是 8 次顺序调用**（文档 D §0.3）。因此"每段耗时"不能直接查表，只能从日志两类带注释的行还原：

- **段级 milestone**：`== XXX metrics elapsed=... ==`，代码画了计时圈的粗粒度锚点。
- **算子级 proving layer**：`proving layer "<op>"`，`backward_iter` 逆拓扑循环（prover.rs:671）每跑一个节点打一行；相邻两行时间戳差 ≈ 该节点 sumcheck 耗时。

**两个口径陷阱（决定本文判定），先钉死：**

1. **"Claims generation ~323s/669s" 不是纯段④，而是 ④+⑤ 包在一起。** 源码落点是 `prove_chunk` 里 `output_claims_by_port`(:583)/`chunk_output_claims`(:627)（真正段④，只占几百 ms）＋ `for (...) backward_iter → op.prove`(:671-808)（段⑤，272 个节点×逐轮 sumcheck）。日志的 `Claims generation metrics` 计时圈把**这一段倒序循环整体**量了进去，所以 84% 这个数字实际是 **⑤ 的 sumcheck 主导**。
2. **段② 没有独立计时点**。域化 i64→Fr 是 `output_tensors().to_field().pad_next_power_of_two()` 随取随弃的动作，代码里不单独成段（文档 D:118 明示）。日志里能对上的是 `Witness context`（域化+承诺整体）。

> **这就是 8 段作为"硬件分割"第一处不合理**：④(claims 生成) 与 ⑤(sumcheck) 在**代码上是同一个倒序循环的"立 claim"+"证 claim"两步**，耗时混在一起、挑战时序串行，无法物理切成两块各自独立跑——一拆就必须在每次立 claim 后往返挑战/中间态，交互爆炸。

我用脚本把两个 log 都还原了（`zkml/tools/extract_prove_timing.py`），结果见 §0 表与 §2 明细。

## 2. 实测明细：节点级 sumcheck（段⑤）按算子类别

同一模型图（GPT-2 24 层，可证明节点 272），两个上下文下 `proving layer` 都是 259 个配对段；**节点不变，变的是每节点张量 2^n**——正是文档 D 附录 A"sumcheck 实例数≈V 不随 s 涨、但每实例规模随 s² 涨"的实证。

| Softmax | 12 | 63.16s | 19.9% | 5.47s |
| EinSum(矩阵乘) | 73 | 40.38s | 12.7% | 8.30s |
| GeLU | 12 | 38.94s | 12.3% | 3.39s |

| Add(残差) | 24 | 2.20s | 0.7% | 107ms |

**s=1024**（配对 sumcheck 合计 ~663s）：

| 类别 | 次数 | 总耗时 | 占比 | 单次最长 |
| --- | --- | --- | --- | --- |
| Softmax | 12 | 214.50s | 32.4% | 18.77s |
| Requant(重量化) | 98 | 181.47s | 27.4% | 2.50s |
| GeLU | 12 | 67.81s | 10.2% | 5.80s |
| EinSum(矩阵乘) | 73 | 64.29s | 9.7% | 8.42s |
| CasualMask | 12 | 47.92s | 7.2% | 4.10s |

| LayerNorm | 25 | 37.35s | 5.6% | 1.95s |
| Add(残差) | 24 | 4.57s | 0.7% | 219ms |

**判读：**
- **Softmax 与 Requant 是 s 涨的"扩音器"**。s=512 时 Requant 最大、Softmax 次之；s=1024 时 Softmax 反超最大（214s，占 32%，因为单次 512² 变 1024²，score 二次项 λ 的 sumcheck 轮多项式按 s² 涨）。CasualMask 也在 s² 上（47.9s，7.2%）。**长上下文下 softmax/因果掩码/attn-score 这一"注意力二次项"是 sumcheck 里涨得最快的**——支持文档 D 附录 C 风险点 1（s² score 二次项是否可动态求值剪裁）。
- **EinSum(矩阵乘) 次数最多（73 次）但单次未必最大**——块粒度主导。sumcheck 的"并行度在节点间 × 串行在节点内轮次"（文档 D 附录 C 风险 3）。
- **Logits 单节点单次最长**（512→23.08s、1024→44.53s）——输出层单个大 logit 表，是可单独优化的孤立峰值。

## 3. 数据传输逻辑：哪一段之间"不能切"

8 段之间要传的数据量，决定切开点是否成立。核心对象是 **MLE(∇) 求值表**（trace 域化，Fr 32B/元素）：

```
②  i64 张量(8B) ──to_field→ Fr(32B) ──into_mle→ ∇ 表            # 数据底座产生
③  ∇ ──batch_commit──▶ G1 承诺(每 2^20/32MB 一块 1 个 G1 点)      # 主计算
④  ∇ 上采点算 evals(point) ──▶ Claim{点,值}                     # 小块
⑤  ∇ 逐轮 fold/build_uni_poly ──▶ 轮多项式 claims                 # 主计算 + 逐轮
⑥  全部 ∇ ──linear_combination──▶ 1 条 rlc_poly                   # 读全部已承诺块
⑦  rlc_poly 折叠→3点──▶ OpeningProof                              # 主计算
```

**跨段数据量分级：**

| 跨越 | 要传的数据 | 量级(s=512 / 1024) | 可切性 |
| --- | --- | --- | --- |
| ①→② | full_trace + 权重 | 权重 Fr ~4GB / trace i64 ~1.3GB~3.7GB | 一次性搬，**可切**（只喂一次） |
| ②→③ | ∇ 表 | **~1.3GB / 3.7GB (Fr 32B)** | **瓶颈**，但要切也只能搬一次 |
| ③→④ | 只有承诺 + 挑战 | G1 点(小) + 挑战(小) | 可切，但④⑤同体（见 §1 陷阱1） |
| ④→⑤ | claims + 逐轮挑战 | 小，但**逐轮高频** | **不可切**——逐轮交互爆炸 |
| ⑤→⑥ | all claims | 中（claims×chunks） | 可传一次，但同板更优 |
| ⑥→⑦ | rlc_poly + 单点 | 小~中 | 可切，⑦独立成一板可行（MSM 引擎） |
| ⑦→⑧ | OpeningProof | 小 | 可切，⑧本来就在主机侧 |

**两处"切开必爆"边界：**
1. **②③④⑤⑥ 之间反复读 ∇**：②③④⑤⑥ 物理上都操作同一批 ∇（文档 D 贯穿线 3）。若把③④⑤⑥放到不同板，每块板都得**持有/搬入那张 3.7GB 的 ∇ 表**或反复搬——②③之间搬一次已是极限，再往后的段同板内复用它更优。
2. **挑战采样（♯11）**：sumcheck 每轮、每节点依赖上一轮随机点（文档 D 附录 B 关键项 11、附录 C 风险 3）。挑战若留主机，"立 claim→主机采样→发回→证下一轮"循环构成**数千次小包往返**，吞吐被延迟打死。**必须把 Fiat-Shamir 挑战上下放到下放段内。**

## 4. 判定：合理的主链切分是"3 截"，不是 8 段

综合 §1 口径与 §3 数据流，对"多 FPGA"场景给出三段式：

```
┌───────────────────────────────────────┐
│  主机(Host)侧                           │
│  段① 切块/调度 + 段⑧ 序列化/发 Proof    │
│  └ 只喂 full_trace+权重(一次)，收 Proof │
└──────────────┬────────────────────────┘
               │ 一次大批搬入:
               │  权重 Fr + ∇ 表(s=1024 ~3.7GB)
               ▼
┌───────────────────────────────────────┐
│  端到端 prove 内核（同一套板）           │
│  段② 域化i64→Fr→∇  (随取随弃)          │
│  段③ witness 批量承诺(MSM)             │
│  段④ claims 生成(采样内建)             │
│  段⑤ 节点级 sumcheck(主算力,~82%)      │
│  段⑥ 合并 sumcheck + RLC               │
│  段⑦ KZG 打开(MSM)                    │
│  挑战采样(Blake3 Fiat-Shamir) 全内建   │
└───────────────────────────────────────┘
```

**论证要点：**
1. **③④⑤⑥⑦ 必须同体**，理由来自 §3 两处"切开必爆"：∇ 表复用 + 挑战逐轮。这一截的耗时占比 = Global − 段③(4%) − 段⑧，实际 **≈90%+ 全都在这 6 段里**，做成一个端到端内核后每块板只跟主机首尾交互（首：喂 trace+权重；尾：交 Proof）。
2. **段② 不单独成段**，它是 ③④ 前的纯数据变形，随取随弃（文档 D:118 原文），跟 ③ 放一起，不增加切分点。
3. **若一定要在两块板间找唯一物理切点**，最优是 **`⑦ 之后`**（把 ⑦KZG 打开单独一块 MSM 引擎，或 ③⑦ 共用同一块 MSM 引擎做 M0，文档 D 附录 C 的 M0），因为它前后只传小数据（rlc_poly+单点 / OpeningProof），且 MSM 引擎可复用 ③ 与 ⑦。次优是 **`③ 之前`**（MSM 与 sumcheck 分离，但 ④⑤⑥ 仍在 sumcheck 板内端到端跑）。
4. **"8 段"作为文档视角是对的**（它讲清了数据流），但**别把 8 段当 8 块板**。真正交付是"主机 + 端到端证明内核(+可选独立 MSM 板)"。

## 5. 给硬件加速的优先级（从实测排）

按 s=1024 的实测占比，加速投资收益排序：

1. **⑤ sumcheck（~85%）** ← 绝对大头。尤其 Softmax(32%)/Requant(27%)/注意力二次项(CasualMask+attn) 随 s² 涨。软目标：一块 sumcheck 多轮引擎（EQ/fold/uni-poly），块粒度 2^20。
2. **③⑦ MSM（~14%）** ← 引擎复用度高、独立封装简单（Pippenger，32MB/chunk）。M0 起步最值。
3. **② 域化 + ① 搬入** ← 决定 I/O 是否吃满（文档 D 附录 C M2 数据通路双缓冲，32MB/chunk 乒乓）。
4. **挑战采样内建** ← 不是算力但**决定架构成败**，缺失即逐轮爆炸。

### 7.2 核验结论一：trace 数据量公式 **✅ 成立**

文档 D 附录 A 给 `trace_Q(s) ≈ α·s + β·s²`（GPT-2：α=1.29MB、β=2.3KB，i64/8B）：

```
Q(128)  = 1.29·128 + 0.0023·128²  = 165.1 + 37.7 = 203 MB
Q(512)  = 1.29·512 + 0.0023·512²  = 660.5 + 602.9 = 1263 MB ≈1.23 GB  (文档表 ≈1.3GB ✓)
Q(1024) = 1.29·1024+0.0023·1024² = 1321.0+2411.7 = 3733 MB ≈3.65 GB   (文档表 ≈3.7GB ✓)
```

三个点满公式且复现文档表 → **数据量公式自洽、正确**。同时给出文档缺的 Q(128)=203MB。要点：**二次项 β·s² 在 s=1024 已占 65%**（2412MB vs 线性 1321MB），是长上下文 trace 膨胀的主因——这正是"数据量"被低估的提醒。

### 7.3 核验结论二：**『耗时 ∝ 数据量』❌ 不成立——需按"节点结构"重定标**

最硬的矛盾数字：

```
trace 数据量 Q:   Q(1024)/Q(128) = 3733/203 = 18.4×
Global 耗时:     Global(1024)/Global(128) = 786.6/160.3 = 4.9×
商 = 3.7  → 数据涨 18.4 倍，时间只涨 4.9 倍
```

→ **不能"拿数据量字节数直接推时间"**。原因（文档 D §0.3 两条规律早已指出，此处落成数字）：

1. **段③ MSM 只吃 trace 的"线性项"**（实测 8.3×，线性项 Q_lin 恰为 8×：`α·1024/(α·128)=8`）。因为 lookup witness 是 **length-s 张量**（输入/输出域化），**不是** s² 的 score 张量——score 只在 ⑤ 侧出现。所以文档 D "MSM 次数∝ΣQ"应读作 **∝ΣQ 的线性部分**。
2. **段⑤ sumcheck 是"40% s² + 60% 固定权重/近线性"的混合**：
   - **s² 分量实证**：Softmax 20.3×、CasualMask 41.7×（attn-score 那 3~7 个张量按 s² 长）。
   - **固定权重维主导**：EinSum 仅 2.4×——因为 EinSum 的 sumcheck 多项式另一维是**权重模型多项式（s 无关的固定尺寸）**，实例规模被权重维(c≈768→3072 固定)封顶，s 只贡献输入维的 3 个 bit。
   - Requant/LayerNorm 3.3~3.5×：介于其张量是 [s,·] 线性 + 逐元素常数位共同作用。
3. **段⑥⑦ 只 3.0×**：吃的是 claim 数（∝可证明节点数 V≈272，s 无关）× 固定 SRS/承诺，属聚合收尾，随 s 增长远慢于数据。

**Global 为什么下凸（4.9× 反而不到 8×线性）**：它 = 大块 s 无关基座（权重主导的⑤分量 + ⑥⑦ + ③固定开销，估 ≈150s）+ 注意力 s² 分量。放大 s 时固定部分几乎不动、注意力部分翻倍，整体取加权和 → 增长率被基座"磨平"。用两端点幂律估：**Global ∝ s^0.77**（介于亚线性；若用二次拟合得 b<0，同样证非 s² 主导）。
