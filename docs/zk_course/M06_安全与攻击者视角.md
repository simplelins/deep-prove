## 1. 健全性预算表：把"安全"变成一页会计账

协议的每个环节都贡献逃逸概率。大牛拿到任何系统，第一件事是列这张表（DeepProve 的口径）：

| 环节 | 逃逸概率 | 数量 | 小计 |
| --- | --- | --- | --- |
| sumcheck 单轮（≤ d/2¹²⁸，d=6） | ≈2⁻¹²⁵·1.5 | 每实例 n 轮 | — |
| sumcheck 单实例（n=20 轮合计） | ≈2⁻¹²⁰·1.9 | 每节点 1 实例 | — |
| sumcheck 全部实例 | ≈2⁻¹²⁰·1.9 | V ≈ 500（GPT-2 量级） | ≈2⁻¹¹¹ |
| PCS 打开（HyperKZG） | ~2⁻¹²⁸ | 每 chunk 1 次 | 2⁻¹²⁸ |
| batched sumcheck 的 γ 组合 | ~2⁻¹²⁸ | 每 chunk 1 次 | 2⁻¹²⁸ |
| chunk 间 seed 链/边界承诺 | 绑定性归入 PCS | — | — |
| **合计** | | | **≈2⁻¹¹¹（由 sumcheck 实例数主导）** |

**读表的两条纪律**：①逃逸概率相**加**（攻击者只需一条路），所以最弱的环节决定水位——没有"平均安全"；②每个数字要有出处（挑战熵 2¹²⁸ 来自 S05 的 16 字节 XOF 口径；d 来自 S06 的轮多项式次数）。**给不出出处的安全数字 = 营销。**

## 2. 亲手实施第一个攻击：statement binding（陈述绑定）

**场景**：V 要验证"承诺为 C 的表，总和 = 6"。协议：P 跑 sumcheck（S06）→ 终点主张 f(7,4) = 11 → V 用 C 打开核销。

**漏洞设定（导师给学生的坏协议）**：transcript 里**忘记吸收 C**——挑战 r = (7,4) 只依赖 sumcheck 消息，不依赖"承诺的是哪张表"。

**攻击**：作弊者根本不用碰 sumcheck——它的消息是 f 的、原样重放。他只需**事后**提交一张在 (7,4) 处取值为 11 的新表。从 S08 知 eq((7,4),·) = [5,5,2,2]，所以：

```
g = [10, 0, 0, 0]   →   g(7,4) = 5×10 + 0 + 0 + 0 = 50 ≡ 11 ✓  (mod 13)
```

V 的全部检查：①sumcheck 消息自洽（与表无关，通过）；②终点主张 11 ✓；③打开 C_g 在 (7,4) 得 11 ✓——**全部通过**。V 被迫接受"g 的总和 = 6"，而 g 的真实总和是 10。**一张自选的表 + 重放的证明 = 伪证。**

**修复 = 协议顺序**：承诺必须**先于**挑战进 transcript（真实系统的顺序：承诺 → 吸收 C → 派生 r → sumcheck → 打开）。修好后 r 依赖 C，攻击者想找"g 在新 r 处 = 声称值"就要在 2⁻¹²⁷ 概率下撞点——回到 S05 的老账。**你刚体验的攻击有一个正式名字：statement binding 缺失**；它的真实受害者见 §4。

**再进一步（攻击者视角的深化）**：即使吸收了 C，攻击者还可以**磨**（grinding）——反复换自己的新鲜表重跑协议，赌挑战恰好落进可乘之机，每次 ≈ 2⁻¹²⁷。防御：让每次磨的成本足够高 + 熵足够大。**攻击者视角永远问：哪一步可以离线重试？**

## 3. 真实世界的事故（只列名字与教训，细节按名检索）

| 事故 | 教训 | 对应本课程 |
| --- | --- | --- |
| **Frozen Heart** 系列（Trail of Bits, 2022） | 多个主流实现（Plonky、Dusk 的 Plonk 等）的 Fiat–Shamir transcript 缺陷：漏吸收、错吸收、挑战派生错误 → 完全可伪造 | §2 的"顺序即协议"+ FPGA 文档附录 A 的标签表 |
| **Binance "Alice"** 资产伪造（BSC, 2022） | 旧证明在**新陈述**上重放（statement binding 缺失） | §2 你刚实施的攻击的工业版 |
| **Zcash 反超发漏洞**（BCTV14，披露于 2018/19） | 承诺方案内部碰撞 → 可以凭空铸币 | 承诺绑定性（S07）不是可选性质 |

**模式**：三类事故对应三种绑定缺失——绑挑战（FS）、绑陈述（replay）、绑承诺（碰撞）。**审计 = 逐一检查这三种绑定。**

## 4. 本仓库的攻击面清单（从源码读出，逐条已核）

1. transcript 吸收顺序/字节格式（附录 A 标签表；`read_challenges` 连续同值的实现现状——挑战熵按现状计）；
2. chunk seed 链的重放顺序 = 完成顺序（streaming 语义）；批式验证的公共挑战口径不同——两条路径不能混；
3. 边界承诺相等（相邻 chunk 对同一张量）——绑定的强度 = MSF；
4. **量化溢出不在证明范围内**（S02：域化一致性以 i64 不溢出为前提）——溢出检查是模型编译期的责任，审计时别漏掉这条"证明范围之外"；
5. 采样随机性（论文 §4.3.6：种子要用可验证随机数来源）；
6. `read_challenges`/`append_and_sample` 的任何一处新增吸收点必须两侧同步 + 登记附录 A。

## 5. 审计清单（可执行的 8 步，照单执行）

1. 画出 transcript 的**完整吸收序列**（逐字节），与附录 A 比对；
2. 找出**所有**随机挑战派生点，确认吸收先于派生、无遗漏、无重复；
3. 检查每个 challenge 是否被**绑定到具体陈述**（表/语句/公共输入）；
4. 列健全性预算表（§1 格式），标注每个数字的出处；
5. 检查"证明范围之外"的假设（溢出、采样、输入合法性）是否有编译期/应用层兜底；
6. 找离线可重试点 → 估算 grinding 成本；
7. 检查跨实例/跨 chunk 的重放面（旧证明能否在新陈述上使用）；
8. 用负例测试固化：每个"应拒绝"的构造写成回归测试（S06 P2 的纪律）。
