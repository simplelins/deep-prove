# M04 · 查表论证全景：从 Plookup 到 Lasso/Jolt

> S09 教了 LogUp——但它是谱系上的第三/四代。本讲把整条谱系摊开：**每一代都在削减"必须承诺的东西"**——Plookup 要排序并承诺整张表，Caulk 把表承诺挪到一次性，Lasso/Jolt 干脆**不承诺大表**。这是 S10"虚拟主张"原则（验证方能算的/能省的都不承诺）在查表方向上四年的演进史。你会在 S09 的玩具表上亲手验证 Plookup 的"差分劈开"恒等式，并最后回答：DeepProve 为什么选 LogUp-GKR。
> 前置：S09（LogUp 全程）、M01（地图轴三）、M02（域与承诺的取舍）。

## 1. 谱系主线（先给结论）

```
2020  Plookup        证明"查询在表里"：排序合并 + 差分劈开        （要排序、承诺整表）
2022  Caulk/cq/Baloo 表预先承诺，查询 = 子向量证明                （去排序；表承诺挪到一次性）
2023  LogUp          多重度 + 对数导数分数和                      （去排序；多列/多集自然；S09）
2023  LogUp-GKR      分数折叠树 + GKR 分层                        （可批量；DeepProve 选择）
2023  Lasso          分解式查表：大表 = 小承诺表的组合             （不承诺大表！）
2024  Jolt           把 RISC-V 每条指令的语义做成 Lasso 查表       （zkVM 提速器）
```

一句话总结四年的方向：**承诺的清单越来越短**。

## 2. Plookup 的核心直觉：排序合并 + 差分劈开（玩具可验）

**想法**：把"查询 ⊆ 表"翻译成"表与查询的**排序合并序列**的相邻差，恰好把表的相邻差**劈开**"。

玩具（S09 同款表）：T = [1, 2, 3, 4]（mod 13），查询去重后 F = {1, 3}。合并排序：

```
s = [1, 1, 2, 3, 3, 4]        （f ∪ F 的多重集排序：查询 1 插在两个 1 之间，3 同理）
```

**差分劈开恒等式**：表的环形差 = {1, 1, 1, −3}（即 1→2, 2→3, 3→4, 4→1 的 −3）；s 的环形差 = {0, 1, 1, 0, 1, −3}。逐一核对"表的每个差 = s 中落在该区间内的差之和"：

```
+1（1→2） = 0（1→1） + 1（1→2）  ✓      查询 1 把表差劈成了两半
+1（2→3） = 1（2→3）             ✓      无查询插入
+1（3→4） = 0（3→3） + 1（3→4）  ✓      查询 3 劈开
−3（4→1） = −3                   ✓      wrap 段无插入
```

**为什么这条恒等式 ⟺ 查询合法**：只有当每个查询值都落在表里（且次数被正确记录）时，合并序列才恰好把表差劈成"和不变"的小段；多查一个表外的值会引入一个不属于任何表区间的差。验证方式：V 掷随机挑战，把两侧的差分序列用**随机权重的乘积式聚合**压成少数几个多项式检查（Plookup 原文用相邻差的线性形乘积；后来 LogUp 把这一步换成了对数导数分数——同族思想的两代实现，LogUp 那代免排序且天然支持多列）。

**诚实边界**：Plookup 原文还有两块本讲不复现的机制——①"域上没有大小序"，"排序"本身要用 0/1 标志位 + 额外约束去证明；②完整的商式检查（原论文 §2.1）。这正是它复杂度的来源，也是下一代要干掉的东西。深挖任务见作业 3。

## 3. Caulk / cq / Baloo（2022–23）：把表承诺挪到"一次性"

Plookup 每次证明都要把**整张表的多项式**卷进协议——表 6.5 万格就得每次付 6.5 万格的代价。Caulk 的改法：**表在 setup 期承诺一次**；每次证明只需证明"查询值对应表的一个**子向量**"——用表承诺的"部分打开"完成。cq/Baloo 把它推广到多查询、任意子表。

**代价转移**：查询侧变便宜了，但要求**表是静态的**（承诺一次反复用）——对"每层都在换表的 LLM"不友好，对"一张巨大固定表"（如椭圆曲线标量乘的位分解表）正好。子向量打开的思想后来被折叠族吸收（M05）。

## 4. Lasso + Jolt（2023–24）：连表都不承诺

谱系的激进一代。Lasso 的洞察：一张大表 T: [m] → F 可以分解成**若干张"数字表"的线性组合**——承诺 K 张长度 log(m) 的小表，就能虚拟出长度 m 的大表，承诺开销从 O(m) 降到 O(K·log m)。**"现成的"（off-the-rack）查表**：表不用预先承诺，查询时按需组装。

**Jolt** 把这个武器对准了 zkVM 的最大痛点：RISC-V 每条指令的语义（加法/移位/符号扩展…）都做成小查表的组合——程序执行的正确性 = 逐指令查表正确性的总和，VM 的"SNARK-unfriendly"部分被查表吃掉。这使 Lasso/Jolt 在小域（Goldilocks/M31）+ 哈希承诺的生态里成为 zkVM 的事实标配。

**与 LogUp 的关系**：不是替代，是**适用域互补**——Lasso 的分解要求表有"数字分解"结构（位宽驱动的表），LogUp 要求"多重度记账"结构。两者都是"少承诺"哲学的孩子。

## 5. 四代对比总表（决策用）

| 维度 | Plookup | Caulk/cq | **LogUp-GKR** | Lasso/Jolt |
| --- | --- | --- | --- | --- |
| 排序 | **要**（域上无序，需额外机制） | 不要 | **不要** | 不要 |
| 表承诺 | 整表、每次 | 整表、一次性 | setup 表 + witness（S08 收口） | **不承诺大表** |
| 多列（位切片） | 别扭 | 单列为主 | **自然**（S09 §4 的 α_col 合并） | 经数字分解支持 |
| 多实例批量 | 弱 | 弱 | **天然**（GKR 折叠树，S09 §5） | 天然 |
| 证明大小 | O(1) 配 KZG | O(1) | O(log·层数) | O(log·K) |
| 甜点负载 | 小表 + 最小证明 | 巨大静态表 | **每层动态小表 + 位宽切片** | VM 指令语义、位运算重 |
| 代表系统 | 早期 Plonkish | 专用查表链 | **DeepProve** | Jolt-RISC-V |

## 6. DeepProve 的选择账（为什么是 LogUp-GKR）

回到它的负载：**每个查表层的表是动态小表**（位宽 16 → 6.5 万格 × 若干位切片列），**每层多实例**（序列里每个位置都要查），**域是 BN254**：

- 排序？6.5 万格 × 每层每实例 → 排序代价不可接受 → 排除 Plookup；
- 表静态？**不**——witness 里的查询/输出每层都变 → 排除 Caulk 系的"一次性承诺"红利；
- 多列 + 多实例批量？LogUp-GKR 的折叠树天然吃下（α_col 合并列、多实例并轮）——**正中靶心**；
- 证明大小？LogUp-GKR 产 log 级证明，收口后并入 batched sumcheck（S08）——与系统其它部分同构。

**对称的边界**（M01 的纪律）：如果负载换成"一张 2³² 的固定指令语义表、百万条指令"——LogUp-GKR 的多重度承诺会爆，Lasso/Jolt 碾压。**没有最好的查表，只有配得对的查表。**
